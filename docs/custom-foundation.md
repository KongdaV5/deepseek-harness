## Foundation and validation scope

P-UPSTREAM-0.2-M1 starts from the exact official `dsh-v0.2.0-rc.2` tag on `migration/upstream-0.2-rc2`. The trusted `feature/codex-subscription` branch remains unchanged. The original Custom ancestor is `dsh-v0.1.6-alpha.2`. The official target stays fixed throughout this package.

The candidate adopts the official Config, ConfigEditor, profile composition, agent-preset architecture, Session V4 codecs and immutable generation publisher. Custom state is limited to product identity, Local inventory, non-secret Codex configuration and mapping, and task authority. The legacy Settings store, settings-file package are absent; the following M1 ledger records the initial foundation, and M2 runtime ownership is recorded below.

## Failure and no-replay obligations

Config translation validates known sections before publication. Unknown sections stay in the archive. A profile digest detects publication-before-archive interruption, and existing profile values protect partial imports from overwriting later edits. Conflicting non-secret auth authority refuses publication.

The official generation publisher retains V3 bytes, validates V4 before exclusive publication and reuses an already published successor. Custom conversion errors produce no canonical V4 generation. Tests allocate private temporary roots; no fixture reads or migrates the formal Custom profile.

Codex intent, accepted, uncertain, pending synchronization, completed-but-not-delivered and unresolved reconciliation fixtures restore as reconciliation-required. A synchronized user-message cursor does not prove answer delivery; only an assistant settlement matching the reconciled DSH turn and step does. A recovery classification is never a dispatch authorization. Task admissions are process-local, not recovered from stored events; durable checkpoint revisions and completion evidence remain the only task authority.

## Launch entry closure

`P-UPSTREAM-0.2-M3-LAUNCH-CLOSEOUT` closed the remaining launch-entry question. The promotion retry had been performed by executing the bundle's internal executable directly, because `open -a` appeared to start nothing, and both the promoted 0.2 application and the 0.1.6 rollback application are ad-hoc signed without notarization, so `spctl` rejects both. Gatekeeper was not the cause: neither bundle carries a quarantine attribute, strict code-signature verification passes for both, and LaunchServices holds a correct registration record for the installed bundle.

The cause was environmental. `open` forwards the caller's environment to the launched application, and Electron treats a non-empty `ELECTRON_RUN_AS_NODE` as an instruction to run as plain Node.js instead of starting the application. An `open` invocation issued from an environment that exports `ELECTRON_RUN_AS_NODE=1` therefore made the bundle's main executable start as Node, emit no application output, and exit in about 65 ms. LaunchServices did start the process; it terminated before presenting a window, which is why the attempt looked like a failure to launch. The launchd user session does not define the variable, so it originates from the calling process rather than from the system, and both the 0.2 application and the 0.1.6 rollback degrade identically under it.

With that variable absent the standard entry points work with no product change. `open -a` starts the application, and having Finder open the bundle is equivalent. The installed smoke was repeated through LaunchServices and passed: the window was presented and visible, the production Custom profile and its canonical patch were used with the patch left untouched, previously persisted Sessions were listed and one was restored, the model selector left the loading state and settled, Local reported a concrete stopped state with its endpoint, and Codex reported ready with the system runtime and its model count. No source change was made, and no synthetic timeout, UI-side hardcoded state or duplicate catalog store was added for this entry point.

Because the variable only affects launching from a shell that already exports it, such as the embedded terminal of an Electron-based host application, a normal Finder launch is unaffected. This is a launch-environment note, not a product defect.
